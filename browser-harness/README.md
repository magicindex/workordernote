# 浏览器测试约定（本机）

## 默认浏览器：飞牛应用商店的 fygo-browser

本机只有一个浏览器 —— 飞牛应用商店安装的 **fygo-browser**，它常驻一个带 CDP 的
**有头**实例。所有浏览器测试（尤其有头测试）都用它。

| 项目 | 值 |
| --- | --- |
| 应用 | `fygo-browser`（飞牛应用中心 `/vol1/@appcenter/fygo-browser`） |
| 内核 | Chrome/152.0.7977.82 |
| 可执行文件 | `/vol1/@appcenter/fygo-browser/app/vendor/runtime/usr/lib/chromium/chromium` |
| CDP 地址 | **http://127.0.0.1:16003** |
| 进程参数 | `--remote-debugging-address=127.0.0.1 --remote-debugging-port=16003 --remote-allow-origins=*` |
| 用户数据 | `/vol1/@appdata/fygo-browser/{profile,cache,config}` |

### 为什么用它

- 它是本机**唯一**的浏览器，也是你自己在用的那一个，内核 152 比测试容器里的 124 新得多，
  渲染、字体、点击命中与你实际所见一致；
- 系统里没有 `xdg-settings` / `xdg-open`，没有 XDG 默认浏览器机制可用，
  因此「默认浏览器」在本机就落在测试入口的默认配置上（即本目录的 `harness.js`）。

### CDP 只监听 127.0.0.1

调用方若在容器里跑，**必须加 `--network host`**：

```bash
docker run --rm --network host -v "$PWD":/w -w /w node:20-alpine node your-test.js
```

## 用法

```js
const { withTab, sleep, clickButtonByText, hasHeading } = require('./harness');
const { login } = require('./reminders-app');

await withTab(async (page, ctx) => {
  await login(page);                       // 登录「工作序记」
  await clickButtonByText(page, '版本信息'); // 打开弹窗
  await sleep(600);
  // ...断言...
  console.log('页面错误:', ctx.errors);
});
```

`withTab` 负责生命周期：连接 → `newPage()` 开自己的标签页 → 跑测试 → **`page.close()`** →
`disconnect()`。

## 两条硬约定

1. **只开自己的标签页，测完关掉。** 绝不调用 `browser.close()` —— 那会关掉你正在用的浏览器。
   用 `withTab` 就自动满足。
2. **覆盖默认值用环境变量 `BROWSER_CDP_URL`**，不要在脚本里写死别的地址。
   容器化的 headless（`zenika/alpine-chrome`）只作为临时兜底，不再是默认。

## 覆盖默认值（临时）

```bash
BROWSER_CDP_URL=http://127.0.0.1:9222 node your-test.js   # 例如指向容器内的 headless
```

## 自动拉起浏览器

`harness.js` 的 `ensureBrowser()` 逻辑：

1. 探 CDP `http://127.0.0.1:16003`；通 → 直接用商店那个有头实例，什么都不动；
2. 不通 → 用**同一个内核 + 独立 profile + 另一个端口 16099** 拉起兜底实例。

为什么不直接用 16003 起兜底：那会占住商店应用的端口，等用户从应用中心启动浏览器时
会因端口被占而失败。独立 profile 也是同理——避开 Chrome 的 SingletonLock。

拉起时必须带上应用自带的运行库路径，否则报 `libopenh264.so.7: cannot open shared object file`：

```
LD_LIBRARY_PATH=/vol1/@appcenter/fygo-browser/app/vendor/runtime/usr/lib/x86_64-linux-gnu:
                /vol1/@appcenter/fygo-browser/app/vendor/runtime/lib/x86_64-linux-gnu:
                /vol1/@appcenter/fygo-browser/app/vendor/runtime/usr/lib
```

有 `DISPLAY` 才是有头；没有（纯 shell）会退回 `--headless=new`，并在日志里如实标注。

> ⚠️ **不要从自己的账号跑 `/vol1/@appcenter/fygo-browser/app/scripts/start.sh`。**
> 实测它会删 `app.sock` 并在权限不足处中断，把应用留在半停止状态（chromium 被收走、
> gateway 还在）。恢复方式是到飞牛应用中心重新启动该浏览器。

## 已知坑（都已在代码里规避）

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 脚本静默什么都不做、退出码 0 | 上一行 `const f = ...` 结尾没分号，下一行以 `(` 开头的 IIFE 被 ASI 并进了上一行的表达式，函数没被调用 | 每个语句都写分号 |
| 导航 60s 超时 | `waitUntil: 'networkidle2'` 在干净 profile 下等不到空闲（应用常驻 SSE） | 改用 `domcontentloaded` + 轮询等待 |
| `page.$` / `page.type` 挂住 | 无显示服务的兜底实例上这两个 API 不返回（`page.evaluate` 正常） | 一律用 `evaluate` 操作 DOM；表单赋值走原生 setter + `input` 事件 |
| `page.evaluate` 里提交表单后卡死 | 该 evaluate 触发导航、执行上下文被销毁，Promise 永不 settle | 提交用 `void page.evaluate(...).catch(()=>{})`，不 await |
| `waitForFunction` 卡住 | 依赖注入脚本轮询，部分环境不返回 | 用 `harness.waitFor()`（evaluate 轮询）替代 |
| 兜底实例用久了对 `page.$` 无响应 | 实例自身进入僵死 | 清掉 profile 后重跑即可（注意 `pkill` 用 `[b]` 写法避免匹配到自己的命令行） |
| **登录态怎么也存不住、页面反复回到登录页** | **Chrome 的 profile 目录路径含非 ASCII 字符（如 `…/编程开发/…`），localStorage 落盘静默失败** | profile 必须放纯 ASCII 路径（默认已改为 `/vol1/@apphome/fn-deepseek-harness/dsh-browser-profile`） |

## 登录：用 API 注入 token，不走 UI 表单

`reminders-app.js` 的 `login()` 优先调 `/api/auth/login` 拿 token，再写进
`localStorage['reminders.token']`。注意**写入时机**：必须在应用启动流程跑完之后写。
应用启动时会调 `/api/bootstrap`，若判定未登录就 `clearSession()`——在启动中途写入的
token 会被它顺手清掉（哪怕只写了别的键，也会连同一起被清）。

## 推荐用法：直接在宿主机跑

宿主机有 Node v24，直接跑即可，这样 `ensureBrowser()` 才有权启动浏览器：

```bash
cd /vol1/@apphome/fn-deepseek-harness/编程开发/browser-harness
APP_URL=http://192.168.3.201:8906 node verify-ux.js
```

放进容器跑也可以连商店实例，但**无法自动拉起**（容器起不了宿主进程）。

`verify-096.js` 的注意点（0.12.0 起）：
- **内网 http 不是安全上下文**：`navigator.serviceWorker` 在这种源上**根本不存在**（不是「没注册」），
  `beforeinstallprompt` 也不会来。用例要按 `window.isSecureContext` 分支断言，否则一跑生产
  （`http://192.168.3.201:8906`）就 `Cannot read properties of undefined` 崩掉——本地用 `127.0.0.1`
  跑是安全上下文，看不出这个问题（本轮真踩）。


- **IIFE 前面一定要有分号**。上一条若是表达式语句（例如 `const f = (x) => y(...)`）且没有分号，
  紧跟的 `(async () => {…})()` 会被解析成「调用上一个函数的参数」——整个用例体永远不执行，
  症状是**脚本静默退出、一行输出都没有**（本轮为此排查了很久）。别指望 `node --check` 发现，它合法。
- **本机 Python 处理绝对路径会失败**：工作目录含中文（编程开发）而默认 `LANG` 为空时，
  `open('/vol1/.../编程开发/x')` 直接 `FileNotFoundError`。要么 `export LANG=C.UTF-8`，
  要么用相对路径。Java 那次（JDK 加载原生库）是同一个根因。
- **HTTP 缓存会骗过断言**：manifest / 公共配置这类「文件名不变、内容会变」的资源，
  浏览器里 `fetch` 可能拿到旧内容（本轮踩到：SW 把 manifest 缓存了，用例读到旧清单）。
  取静态文件用 `{ cache: 'no-store' }`，或者干脆在 Node 侧取。
- **刷新是否真的重新请求**别 patch `window.fetch`：axios 走 XMLHttpRequest，
  用 `performance.getEntriesByType('resource')` 数更可靠。
- 工具栏那种自定义类里**不要写 display**：`.toolbar-btn { @apply inline-flex … }` 的优先级高于
  Tailwind 的 `hidden`，手机上藏不住；display 交给使用处的 `inline-flex` / `hidden sm:inline-flex`。

`verify-013.js` 的几个注意点：

- 主题用例会**真的改用户配置**，所以开头记下原值、结束时（失败也走 `finally`）恢复。
- 配置项的保存是「改 select 标记未保存 → 点这一行的保存按钮」两步，而且 Vue 异步更新 DOM：
  change 派发完立刻点，按钮还是 disabled 的。用例里两步之间留了 300ms。
- 深浅色断言留了大余量（上海 9–16 点必定白天、20–次日 6 点必定夜间），

`verify-export.js` 有两个实现上的坑，改它之前先看一眼：

- 导出的下载是 `axios(blob)` + `a.click()`，所以断言挂在**那次 XHR 的响应**上；
  而 BOM 在浏览器的 `response.text()` 里会被解码器吃掉，要用页面内 `fetch` +
  `arrayBuffer()` 读原始字节才验得出来。
- 浏览器 profile 是共用的，上一次用例留在 `localStorage['ui_completed_lists']` 的
  清单筛选会让「已完成」导出变成 0 行；用例开头会先清掉这个键。


`verify-export.js` 的时间段断言不是只看「条数大小关系」，而是：先用 `range=all` 把全部完成记录
导出来，在用例里**按同一套口径独立分桶**（今天/昨天/本周/本月/上月/今年），再和每个时间段接口
返回的条数逐一比对。后端区间算法改错（比如上月算成上上个月、昨天少一天）会立刻红。
唯一需要注意：某个时间段恰好没有数据时该断言是「0 == 0」，所以沙箱里曾临时往 `completions`
插一条昨天的记录跑一遍（跑完删掉），确认昨天那条真能被查出来。

## 一条硬规矩：改用户配置的用例必须回读确认

`verify-ux.js`、`verify-013.js` 会真的改用户配置（默认首页、主题模式、日出日落位置）。
血的教训：还原那一步写成「派发 change → sleep → 点保存」，而 Vue 是异步更新 DOM，
change 刚派发完保存按钮还是 `disabled`，点击静默失败 —— 结果**生产上的 `default_view`
被留在 calendar、`sun_location` 被留在 beijing**，用户自己不说根本发现不了。

现在两个用例的还原步骤统一成：改值 → `waitFor` 按钮可点 → 点击 → **回读
`/api/configs/user/meta` 确认** → 不一致再试一次 → 断言「已还原为原值」。
新增用例照抄这个模式，别只写「点一下就完事」。

另外两条（0.2.0 补）：
- `verify-ux` 的第 1 步会改「默认首页」。原值现在**从服务端读**，保存后**回读服务端断言**，
  还原后再确认；它后面的检查也改成显式走 `/admin/all`——否则这个设置一旦被留在「日历视图」，
  后面依赖列表页的检查会一起变红（当时就是 3 项一起红，实际根因只有一个）。
- 打印相关用例用 `page.emulateMediaType('print')` 量排版时，**视口要按「可打印区」设**
  （A4 横向 1123px 减去左右各 12mm ≈ 1033px），按整张纸宽量会把正常排版误判成溢出。
  `page.pdf()` 在这个有头 Chrome 上不认 CSS 的 `@page size`（会退回 Letter），
  要验纸张就显式传 `width/height/margin`。

## 0.13.1 的几条经验（2026-10-08 记）

- **跨月账期**：`currentPeriod` 必须从**上个月**开始找「还款日未过的最早一期」。从当月开始找时，
  账单日 25 / 还款日 19 这类卡会跳过正在还款的那一期，卡面颜色永远不变（用户报的 bug）。
  用例 `TestCardCurrentPeriodCrossMonth` 钉住；前端 `urgencyOf()` 依赖 `card.current`，所以修这里就够。
- **「刷新」要刷新整页**：卡片面板的刷新按钮一开始只调了 `load()`，头部时间卡片（自己管数据）
  没跟着刷，界面看起来「点了刷新没反应」。现在刷新时 `emit('refresh-strip')` 让父组件 +1
  `refreshKey`。**这类「同一页两个数据源」的地方，改动时要想清楚刷新链路。**
- 头部卡片的 DOM 属性从 `data-week-*` 改名为 `data-billing-*`（口径已经不是「一周」了）。

- **完成记录撤回**：`completions` 原来是硬删除，同步里没有墓碑，「标记已还 → 同步 → 撤销已还」
  会在对端留幽灵记录。改成 `gorm.DeletedAt` 软删 + 快照 `Unscoped()` 带墓碑后，
  Go 用例 `TestCompletionRetractionSyncsToPeer`（两个库跑完整 A→B 往返）钉住了行为。
  **坑**：`*time.Time` 不会被 GORM 认成软删除字段（`Delete` 照样是真删、`Unscoped()` 也没用），
  必须用 `gorm.DeletedAt`；本轮因为这个白跑了几次测试。
- **别拿旧镜像当新代码跑**：改完 Go 一定要重新 `docker build --target backend-builder`，
  否则 `docker run go-builder:...` 跑的还是上一版二进制，症状是「明明改了却报原来的错」。
- `verify-052` 新增两条：设置组**展开后刷新要回到收起**、**不再写 `ui_settings_open`**。

最后汇总套件数与项数，方便和发布说明里的数字对照。

## 三台数据指纹：`fingerprint-instances.py`（2026-10-09 记）

发版收尾要核对「201 / 200 / 沙箱三台数据一致」。**不能用 id 比**——id 是各实例自己的本地 id
（沙箱还是整目录拷过去的），跨机必然不同。这个脚本按内容算四个 sha256 前 10 位：

```bash
python3 fingerprint-instances.py                                   # 默认 201 / 200 / 沙箱 8908
python3 fingerprint-instances.py http://127.0.0.1:8906 http://192.168.3.200:8906
```

- 清单：`名字 + 模板 + 图标`；卡片：`卡名 + 银行 + 卡号 + 配色`；
  提醒：`标题 + 类型 + 清单名 + 到期 + 完成时间`；完成记录：`标题 + 完成时间`。
- 排序后拼串再哈希：**只比内容，不比顺序**（顺序另有断言）。
- **沙箱与 201/200 不一致是正常的**：沙箱同步恒为 `off`（防止测试数据流进生产），
  它只是某一刻的快照；201 与 200 之间才是「必须一致」。脚本会把不一致的项标出来，
  但别把沙箱的落后当成故障。

## 不要在一次回归**跑着的时候**改 `run-all.sh`（2026-10-10 记）

上面「0.14.0 以后新增的套件」那张速查表里。

## 别把「页数 / 行数」这类数据量写死（2026-10-12 记）

## 写系统配置的 Go 用例：先 `InitDefaultConfigs`，否则写进去读不到（2026-10-11 记）

`sysconfig.UpdateConfig` 在**行不存在**时新建的行 `public=false`，而 `overduePolicy`（以及所有
`GetPublicConfigs` 的读方）只查 `public = true` —— 于是用例里写完配置再断言，拿到的**一直是默认值**
（这轮「过期时间设成 00:00 应该多一条逾期」就是这么假红的）。写法：

```go
sysconfig.InitDefaultConfigs(appDB)          // 先把注册表里的默认值播种好（含 public 标记）
sysconfig.UpdateConfig(appDB, key, val, 0)   // 再改值
resetOverduePolicyCache()                    // 进程内 2 秒缓存也要清
```

另外：**别把「今天几点」写进期望值**。这轮踩了三次钟点坑 —— `now-1h` 当「已过期」的固定用例
（凌晨跑就变成未来）、「今天 09:00 应该算逾期」的断言（04:58 跑时 09:00 还没到）、以及
`verify-112` 用「昨天 23:00」当「肯定逾期」的夹具（0.20 起截止时刻是**当天 23:59 + 宽限 30 分钟**，
凌晨 00:26 跑时宽限还没走完 → 假红）。
凡是和「当天某个时刻」有关的断言，要么用固定日期的 SQL 级核对，要么按当前时钟算期望值，
要么把夹具放到**足够远**：逾期用「前天 23:00」、不算逾期用「今天 00:10」。

0.19.0 起日历的交互变了：**单击任务 → 弹只读查看页，双击任务 → 直接进编辑器**（查看页底部还有

## 通用坑：登录接口有限流（2026-10-06 记）

服务端公开接口默认 **20 次/分钟/IP**（`-rate-limit`，见 `server/server.go` 的 `publicLimiter`），
而**登录接口就在公开组里**。一轮全量回归要登录几十次，很容易撞上 429——症状是「token 拿不到」，
接着整个套件的断言莫名其妙地失败（本轮 `verify-096` 就这么假红过两次，还一度误报成「有效期 0 秒」）。

处理办法（已经在 `reminders-app.js` 里落地，所有套件受益）：

- `loginViaApi` / `login` 遇到 429 会**等窗口再试**（6s、12s、18s…），不要改成「失败就算了」；
- 套件里自己调登录接口的地方（如 `verify-096` 实测 JWT 有效期）也要带重试，
  并把状态码与消息放进断言说明里，免得再被当成「有效期为 0」；
- 别为了让用例好跑就去调生产环境的限流参数。

## 未读的「逾期提醒」弹窗会挡住点击：跑回归前先把未读点掉（2026-10-12 记）

0.21.3 起「到了逾期提醒时间还没完成」会发一条站内提醒（`type=reminder_overdue`），
它和到点提醒一样是**屏幕中央、必须处理的弹窗**（`z-[130]` 的全屏遮罩）。于是：

- 实例上只要留着**未读**的提醒，用例一进页面就会被弹窗盖住；
  `page.mouse.click(x, y)` 全落在遮罩上（`elementFromPoint` 返回的是弹窗里的 div，
  不是 `.cal-cell`），表现成「双击日期格不弹面板」「点遮罩关不掉」这类莫名其妙的假红。
- 本轮全量回归里 `verify-013` / `verify-017` / `verify-reminders` 就是这么红的，
  当时三个套件单跑前先 `POST /api/reminder/notifications/read-all`，立刻全绿。

规矩：**改动用户配置 / 造通知的用例，收尾要把自己触发的通知标为已读**
（`verify-114` 已这么做）；跑全量回归前如果实例上有未读提醒，先点掉或调
`POST /api/reminder/notifications/read-all`（只对测试实例做，别动生产）。

## 脚本自身的坑（2026-10-05 记）

- **`pkill -f 模式` 会匹配到自己的命令行**：`pkill -f "docker build"`、`pkill -f gotest-ctx`
  这类写法，调用它的那个 `bash -c` 命令行里也含同样的字符串，于是先把自己杀了
  （本轮连续自杀两次，输出只有 `[killed by signal: SIGTERM]`）。
  要按 PID 杀就 `pgrep -f 模式` 后过滤 `$$`/`$PPID`，别用 `pkill -f`。
- **`docker build` 的构建上下文别指向杂物目录**：`tmp/` 下有几百 MB 的解压包/测试数据时，
  构建会长时间卡在 `transferring context`，看着像网络问题其实是在传 context。
  给构建单独准备一个只放 Dockerfile 的小目录（`/tmp/gotest-ctx`）即可。
- 本机 apk 源（`mirrors.aliyun.com`）在构建容器里的下载速度会剧烈波动（同一时刻宿主机 `curl`
  很快、构建里只有 ~9KB/s），一次 `apk add gcc musl-dev` 可能从 7 分钟拖到半小时以上。
- **`ARG` 在 `apk add` 之前 = 改参数就重装 gcc**：`Dockerfile.custom` 里 `ARG VERSION/BUILD_TIME/
  GIT_COMMIT` 声明在第 24–26 行，而 `apk add gcc musl-dev` 在第 42 行。用不同的 `BUILD_TIME`
  去构建 `--target backend-builder` 会整层缓存失效（本轮因此白等两次）。想跑 Go 测试就用
  **上次构建时的原参数**，或干脆不传——缓存全中时几秒出镜像：
  `docker run --rm go-builder:0.9.0 go test ./...`（本轮全绿，退出码 0）。

## 「提醒@他」套件（`verify-118`，2026-10-13 新增）

- **这条用例需要第二个账号**：实例上只有一个账号时它会自己临时把 `allow_register` 打开、
  注册一个一次性探针账号（`nudgeprobe<时间戳>`），收尾再**删账号 + 删提醒 + 还原注册开关**。
  在只有一个账号的干净实例上跑也能过（29 项）；`clean-self-test.sh` 不管这类数据，
  被打断后残留的探针账号要手动 `DELETE /api/users/<id>`。
- **开关是系统偏好 `nudge_enabled`**（`ScopeSystem`，一台实例一份，不是个人偏好）：
  关掉后**侧栏入口消失，直接访问 `/admin/nudges` 也会被送回首页**（`NudgeView` 里 watch + onMounted 兜底），
  所以断言「页面不渲染」要用 `[data-nudge-page]` 存在与否，别用「路由 404」。
- **角标口径是「别人提醒我、我还没做完」**（`/summary` 的 `nudge_pending`），**不是未读**：
  对方点过「已收到」但还没点「已完成」时角标照旧挂着，做完才归零。
- **本标签页自己的改动收不到 SSE 回声**：服务端广播按 `X-Client-Id` 跳过发起者
  （`realtime.go` 的 `originClientID`），所以「改完之后侧栏角标要跟着变」必须由页面自己
  `window.dispatchEvent(new CustomEvent('reminder-data-changed'))`（`NudgeView` 的 `changed()`）
  —— 这是所有会改侧栏统计的新页面的通用坑，本轮就是漏了这一步、角标不归零才发现的。
- 站内通知类型：接收人收到 `nudge_received`、发起人收到 `nudge_read` / `nudge_done`；
  它们走**通知中心（消息面板）** 与 toast，**不进中央弹窗**（`ALERT_NOTIFICATION_TYPES` 只有
  `reminder_due` / `reminder_overdue`）。

## 这一批（2026-10-13 晚）三条改动的套件注意点（`verify-119`）

- **`verify-119` 里有一条「等 15 秒看会不会弹窗」的用例**（新建的已到点提醒不该立刻弹）：
  它按的是「新建后至少 10 分钟才第一次提醒」这条新口径（`firstRemindSchedule`，
  Go 侧用例 `first_remind_test.go`）。**别把它改成等 10 分钟** —— 那会把整轮回归拖长十分钟；
  真正的口径由 Go 用例钉住，浏览器这边只验「没有立刻弹」这个用户可见的结果。
- 那条用例造的是**已经到点**的提醒（due = 现在 - 1 分钟），并且**没有**把创建时间做旧：
  这正是要测的场景。它跑完会自己删掉，不会给后面的套件留下会弹窗的条目。
- **生日卡片（年度循环）的断言要按「今天」算**：下一次生日 = 今年的 9/17（已过就明年），
  已过次数 = 下一次那年 - 出生年 - 1。别写死天数（今天是 9/17 的话就是「第 N 次」）。
- 倒计时数字现在是**两层描边**：`<b>` 自己是内圈（深色卡面=黑边），`::before` 那层是外圈
  （更粗，深色卡面=白边）。量样式要用 `getComputedStyle(b, '::before')`；**「就是今天」
  那张卡片的 `<b>` 里是文字、没有 `data-count`**，外圈 content 会是空串 —— 要取
  `b[data-count]` 去断言（`verify-112` 本轮先假红过一次）。

## 清理容器只按名字删（2026-10-13 血的教训）

发版收尾清理临时容器时，我用 `docker rm -f $(docker ps -q --filter ancestor=alpine:latest)`
「顺手」删掉 skopeo 用的 alpine 容器 —— **`--filter ancestor=` 会匹配派生镜像**，
而本项目的 `workordernote` 就是 `FROM alpine:latest`，结果把**201 生产 8906 与沙箱 8908
两个容器一起删了**（数据目录没动，所以只丢了容器、没丢数据；已用 compose 与原来的
`docker run` 参数原样恢复并逐项核对指纹一致）。

- ✅ 只删自己启动的那个：`docker rm -f wsn-iter`（按名字），或者启动时把 ID 记下来。
- ❌ 不要用 `--filter ancestor=<基础镜像>` 批量删：它匹配的是**整棵镜像树**。
- ❌ 也不要用 `pkill -f <模式>`（README 另一处写过：它会先杀掉自己）。
